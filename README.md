# MISOfortune: A Tale Woven Through SPI

Our team project on SPI (Serial Peripheral Interface), written in Verilog and verified in simulation with Vivado. There are four modules, one per team member. Each one has a single SPI master talking to several slaves, and each one shows a different side of the protocol.

Team: Madhuri, Nivetha, Aayush, Akshith

## The story, briefly

A mine collapses. The rescue controller monitors the miners over SPI (Madhuri). A factory above ground keeps cutting cotton for dressings, and its machines have to take turns resting (Aayush). A drone finds the survivors and drops supplies (Akshith). Nivetha's module covers [TODO].

The name comes from the protocol: a slave can only reply on MISO, so every bit of bad news reaches the master on that one line.

## SPI basics

SPI is a synchronous serial bus with one master and one or more slaves. It uses four signals:

| Signal | Direction       | Purpose                                      |
| ------ | --------------- | -------------------------------------------- |
| SCLK   | master to slave | Clock, always generated by the master        |
| MOSI   | master to slave | Data from master                             |
| MISO   | slave to master | Data from slave                              |
| CS     | master to slave | Chip select, active low, one line per slave  |

With several slaves, SCLK, MOSI and MISO are shared and each slave has its own CS. Only the slave whose CS is low drives MISO.

A transfer is a swap. Master and slave each hold a shift register, and on every clock one bit goes out on MOSI while one bit comes in on MISO. After 8 clocks (or 16 for a 16-bit frame) the two registers have traded contents. This is how a slave returns a status byte in the same transaction in which it receives a command.

The mode is set by two bits. CPOL is the idle level of SCLK. CPHA selects whether data is sampled on the first or second clock edge.

| Mode | CPOL | CPHA | Sampled on   |
| ---- | ---- | ---- | ------------ |
| 0    | 0    | 0    | rising edge  |
| 1    | 0    | 1    | falling edge |
| 2    | 1    | 0    | falling edge |
| 3    | 1    | 1    | rising edge  |

Master and slave must use the same mode.

### 01 Time Loop (Madhuri)

Folder: [`01-time-loop`](01-time-loop)

The SPI foundation of the project. A PHY module generates SCLK and shifts data in and out, with the mode set by CPOL and CPHA and with configurable clock divider and chip-select setup, hold and gap timing. A scheduler sits on top and polls three devices in a fixed order: gas sensor, temperature sensor, worker status. For each one it sends `0xA5` and reads back an 8-bit value on MISO, finishing one transfer before starting the next.

The top level logs the replies and sets a sticky alert if gas or temperature is `0x40` or higher, or the worker status is not `0x01`. These values are illustrative, not real safety limits.

Verified: MOSI (`0xA5`) and MISO (`0x3C`) checks in all four modes, zero timing values, reset in the middle of a transfer, scheduler sequencing, and the full integration run with alert cases. The newer nonzero timing assertions still need a confirming run in Vivado.

Files: `spi_phy_m2.v`, `spi_scheduler.v`, `spi_time_loop_top.v`, `spi_slave_mode_model.v` and three testbenches. Open `SPI_TIME_LOOP.xpr` in Vivado 2023.2 to run them.

### 02 Cotton Factory (Aayush)

Folder: [`02-cotton-factory`](02-cotton-factory)

One master and three slave cutting machines, with chip selects CS1 to CS3, in SPI mode 0 with 8-bit frames. The slaves cut 3, 4 and 5 units of cotton per batch. When a slave finishes a batch it asks to rest, and the master sees this when it polls the slave's status over MISO. The master grants rest only if at least one other machine is still cutting, so the factory never stops. A resting slave stays idle for 20 clock cycles and then resumes.

The point of this module is that the system-level rule lives in the master, while each slave is a simple state machine.

Files: `code.v` (modules `cotton_slave`, `spi_master`, `cotton_factory`) and `testbench.v`.

### 03 Drone Strike (Akshith)

Folder: [`03-drone-strike`](03-drone-strike)

One master and four slaves in SPI mode 0. Each frame is 16 bits, MSB first, laid out as `{cmd, dat}`, and the slave returns its status byte on MISO in the same frame. A Python HUD on top sends the commands.

| Slave | Role                                   |
| ----- | -------------------------------------- |
| 1     | Flight control (drone state, aim servo) |
| 2     | Target control (search, found, lock, impact) |
| 3     | Telemetry (mission and hit count on 7-segment) |
| 4     | Fault and game (buzzer, warning LEDs)  |

| Cmd | Meaning       | Cmd | Meaning       |
| --- | ------------- | --- | ------------- |
| 01  | arm           | 06  | return home   |
| 02  | launch        | 07  | abort / fault |
| 03  | start mission | 08  | reset         |
| 04  | target detect | 09  | aim           |
| 05  | execute hit   |     |               |

The slaves enforce the rules. For example, command 05 is ignored unless slave 2 is in the locked state, so an early shot is just a miss. The Verilog testbench writes a trace file that the HUD can replay, so the simulation and the demo match.

Run modes are plain Python, a Vivado testbench check, trace replay, live co-simulation, or a board over UART. See the folder's README for details.

## Running the simulations

You need Vivado for the Verilog (Time Loop was built in 2023.2). The drone HUD also needs Python 3.13 or older with `pygame`, `numpy` and `pyserial`. For any module, add its design files as design sources and its testbench as a simulation source, then run behavioural simulation. Module-specific steps are in each folder.

## Methodology

For each module we followed the same steps: decide what the master sends and what each slave reports, draw the state machines, write the SPI core first and the slaves and master on top, test each piece alone, then test everything together. Testbenches compare received bytes against expected values instead of relying on waveform inspection. Details are in [`docs/methodology.md`](docs/methodology.md), and a longer SPI refresher is in [`docs/spi-primer.md`](docs/spi-primer.md).
