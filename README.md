# MISOfortune: A Tale of Woes Woven Through SPI

Four people, four projects, one wire protocol. This repository collects our SPI work into a single story, so that each module can be read on its own but also makes sense as part of a bigger picture.

Team: Madhuri, Nivetha, Aayush, Akshith

Everything here is written in Verilog and verified in simulation (Vivado), with a Python front end for the drone mission. No hardware is needed to run any of it.

---

## Why "MISOfortune"?

SPI is a lopsided conversation. The master controls the clock, picks who gets to talk, and decides when. A slave can only speak when it has been selected and clocked, and the only line it has for speaking is MISO (Master In, Slave Out).

So every piece of bad news in a system built on SPI, whether it is a machine that needs rest, a sensor that lost its target, or a fault flag, reaches the master through MISO and nowhere else. That is the joke in our title, and it is also the technical idea that ties our four projects together: in each one, a single master is trying to keep a crisis under control by listening to what its slaves report back, one chip select at a time.

---

## The story

It starts underground and ends in the air.

**Chapter 1: The Collapse (Madhuri, SPI Time Loop).** A tunnel collapses in an underground mine. A rescue controller has to keep checking three monitoring devices down there (a gas sensor, a temperature sensor and a worker status unit), and it does so over SPI. Before anything else can happen, the controller needs a reliable way to talk to them at all, so this chapter is where we build the foundation: the signal-level SPI master, support for all four SPI modes, and a scheduler that polls the three devices in turn and raises an alert if a reading looks bad.

**Chapter 2: The Cotton Factory (Aayush, SPI Cotton Factory).** Above ground, the rescue effort needs a steady supply of cotton for dressings, and a small factory is cutting it round the clock. Three cutting machines work in batches of different sizes and each one needs rest after a batch. If they all rest at once, supply stops and people wait. So one master polls the machines over SPI and only grants rest to a machine if at least one other is still running. This chapter is about scheduling under constraints, on top of the SPI foundation from Chapter 1.

**Chapter 3: The Drone (Akshith, SPI Drone Strike).** Supplies are ready, but the survivors have to be found and reached. A drone is launched, searches the area, locks onto a target and delivers its payload. One SPI master commands four slaves (flight control, target control, telemetry and fault handling) while a Python HUD lets the operator aim, lock and fire. This chapter is where SPI becomes a full system with a human in the loop.

## SPI in two minutes

SPI uses four signals. SCLK is the clock, generated by the master. MOSI carries data from master to slave. MISO carries data from slave to master. CS (chip select, active low) chooses which slave is listening. With several slaves, SCLK, MOSI and MISO are shared and each slave gets its own CS line.

Data is shifted out one bit per clock, and the master and slave shift at the same time, so every transfer is a swap: while the master sends a command, the slave is already sending a status byte back.

The four SPI modes come from two settings. CPOL is the idle level of the clock, and CPHA decides whether data is sampled on the first or second clock edge. Mode 0 (CPOL 0, CPHA 0) is the most common and is what the factory and drone projects use. The time loop project implements all four.

## Methodology

We all followed the same basic loop, even though the projects look very different.

1. **Decide what the master needs to know.** Before writing any Verilog, we wrote down what each slave has to report and what the master has to command. In the factory this was "am I busy or asking for rest". In the drone it was the state of the flight and target slaves.
2. **Draw the state machines.** Every slave, and the master where it makes decisions, is a finite state machine. The factory machines cycle between cutting, requesting rest and resting. The drone's target slave moves through searching, found, locking, locked and impact.
3. **Write the RTL in small pieces.** A shift-register level SPI core first, then the slave logic on top of it, then the master that coordinates them. Each piece is testable alone.
4. **Test each piece alone, then together.** Module testbenches first, then an integration testbench with the real master talking to all the slaves.
5. **Check, don't just look.** Where possible the testbenches compare the received bytes against expected values and print a pass or fail, instead of relying on someone reading waveforms. Madhuri's integration testbench checks the expected response bytes from all three slaves, and Akshith's prints each state beside what it should be.
6. **Put a face on it.** The mine rescue theme, the factory, the drone HUD. A story makes the behaviour easier to explain and easier to remember.

## Module documentation

### 01 Time Loop (Madhuri)

Folder: [`01-time-loop`](01-time-loop) (original repository: https://github.com/madhurijolam25-droid/SPI-Time-Loop)

This module is the SPI foundation for the whole project. A scheduler and an SPI master PHY poll three simulated mine-rescue monitoring devices, and a small piece of alert logic checks what comes back.

The scheduler polls in a fixed order: gas sensor, temperature sensor, worker status. For each device it sends `0xA5` and reads an 8-bit value back on MISO. The scheduler starts one transfer, waits for it to finish, then moves to the next device.

| Device             | Safe example value | Meaning in the demo               |
| ------------------ | ------------------ | --------------------------------- |
| Gas sensor         | `0x30`             | Below the demo warning level      |
| Temperature sensor | `0x30`             | Below the demo warning level      |
| Worker status      | `0x01`             | Worker status is OK               |

The top-level design records the replies and sets a sticky `rescue_alert` if the gas or temperature reading is `0x40` or higher, or if the worker status is anything other than `0x01` (`0x00` means distress). The alert clears on reset. These thresholds are illustrative simulation settings, not real mine-safety limits.

The PHY (`spi_phy_m2.v`) supports all four SPI modes through CPOL and CPHA, with configurable SCLK divider and chip-select setup, hold and gap timing. Other files: `spi_scheduler.v`, `spi_time_loop_top.v`, a slave model `spi_slave_mode_model.v`, and three testbenches (`spi_phy_m2_tb`, `spi_scheduler_tb`, `spi_time_loop_top_tb`).

Verification: the PHY passes MOSI (`0xA5`) and MISO (`0x3C`) checks in all four modes, handles zero timing values and reset mid-transfer, the scheduler completes three transfers, and the integration testbench passes the safe case plus gas warning, temperature warning, worker distress and alert reset. The newer nonzero timing assertions in the PHY testbench still need a confirming run in Vivado.

To run it, open `SPI_TIME_LOOP.xpr` in Vivado 2023.2 and run behavioural simulation. Full details are in the folder's own README.

### 02 Cotton Factory (Aayush)

Folder: [`02-cotton-factory`](02-cotton-factory) (original repository: https://github.com/adp-sudo/verilog-spi-cotton-factory)

One SPI master controls three independent slaves, each representing a cotton-cutting machine. The design goal is simple to state: at least one machine must be cutting at every moment.

| Slave | Cotton per batch |
| ----- | ---------------- |
| 1     | 3 units          |
| 2     | 4 units          |
| 3     | 5 units          |

How it works: all three machines start cutting. When a machine finishes its batch it raises a request to rest, which the master sees when it polls that slave over MISO. The master grants rest only if at least one other machine is still active, otherwise the machine is told to keep going. A machine that is granted rest stays idle for a fixed 20 clock cycles and then resumes. The protocol is SPI Mode 0 with separate CS1, CS2 and CS3 lines.

Concepts shown: multi-slave SPI, polling over MISO, finite state machines, a scheduling rule that guarantees a system-level property, and simulation-based verification.

Files: `code.v` (modules `cotton_slave`, `spi_master` and `cotton_factory`) and `testbench.v` (verification).

### 03 Drone Strike (Akshith)

Folder: [`03-drone-strike`](03-drone-strike) (original repository: https://github.com/Akshith1376/spi-drone-strike)

One SPI master commands four slaves, and a Python HUD (inspired by an aerial strike view) sits on top so the mission can be flown with a mouse and keyboard.

```
HUD (Python) -> SPI master -> slave 1  flight control   (drone state, aim servo)
                           -> slave 2  target control   (search, found, lock, impact)
                           -> slave 3  telemetry        (mission and hit count on 7-segment)
                           -> slave 4  fault and game   (buzzer, warning LEDs)
```

Frames are 16 bits, MSB first, in SPI Mode 0, laid out as `{cmd, dat}`. The slave returns its status byte on MISO during the same frame.

| Cmd | Meaning       | Effect                                                      |
| --- | ------------- | ----------------------------------------------------------- |
| 01  | arm           | slave 1 goes from idle to armed                             |
| 02  | launch        | slave 1 goes from armed to airborne                         |
| 03  | start mission | slave 2 receives the target position and starts searching   |
| 04  | target detect | slave 2 locks only if the aim is within one cell of target  |
| 05  | execute hit   | slave 1 fires and slave 2 registers impact, only if locked  |
| 06  | return home   | drone returns                                               |
| 07  | abort / fault | slave 4 sets the warning LEDs                               |
| 08  | reset         | clears state, optionally the score                          |
| 09  | aim           | moves the drone servo to the aimed position                 |

The key idea is that the target slave enforces the rules, not the HUD. Firing before the target is locked is ignored, so an early shot is simply a miss.

Files are kept flat in the folder: the Verilog sources (`spi_m.v`, `spi_s.v`, `s1_fly.v` to `s4_flt.v`, plus `top.v`, `u_rx.v`, `u_tx.v`, `servo.v`, `sseg.v` for the board), testbenches `tb.v` and `tb_x.v`, the Vivado script `xlive.tcl`, and the HUD `strike.py`.

Ways to run it: plain Python mode (uses a Python copy of the slave logic), a Vivado testbench check, replay of a recorded simulation trace, live co-simulation with Vivado, or on a board through UART. Full instructions are in the folder's README.

## How the pieces connect

The time loop module is the layer everyone else stands on: it shows how a master generates the clock, how modes work, and how a scheduler orders transactions. The cotton factory takes that idea of a master polling slaves and adds a rule the master must enforce (never let supply drop to zero). The drone takes it further with a richer command set, four slaves with different jobs, and an operator in the loop.

Read in order, the projects move from the protocol itself, to coordination, to a complete interactive system.

---

## Running everything

You need Vivado for the Verilog simulations (Madhuri's project was built in 2023.2). For the drone HUD you also need Python 3.13 or older with `pygame`, `numpy` and `pyserial`.

General steps for any module: create a Vivado project, add the module's design files as design sources, add its testbench as a simulation source, run behavioural simulation and `run all`. Module-specific notes are in each folder.

## Suggested presentation flow

About one minute per chapter plus a short intro and wrap-up works well.

Open with the pun and the one-line idea: the master talks as much as it likes, the slaves can only answer on MISO, so all bad news travels on one wire. Then walk through the chapters in order. Madhuri shows the waveforms and the four modes, and sets the scene of the mine. Aayush shows the three machines taking turns to rest and points out that the activity never drops to zero. Akshith runs the HUD live or plays the replay, and ends on a lock and a hit. Nivetha closes the chain. Finish by returning to the opening line: same four wires, four different woes, one master in charge each time.
